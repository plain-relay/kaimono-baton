# 有料β準備基準

Status: approved direction

## 目的

有料βは、機能が多いことではなく、利用者へ料金を請求しても個人で安全に運用できることを確認してから開始する。

有料βと一般公開は別の開始判定とする。有料β開始ゲートはSections 1〜13、有料・その他の補助機能のPublic Release / General AvailabilityゲートはSection 14を対象とする。
無料・停止可能な商品写真だけの初回公開には、Section 15の専用判定を適用する。

## 判定ルール

### 有料βの非免除条件

有料β開始時は、Sections 1〜12の全チェック項目とSection 13の開始条件を非免除条件とする。Section 14はPaid Beta開始後の実績を要求するため、有料β開始判定の対象外である。

特に次は人間のリスク受容によって免除できない。

- 顧客安全と無料コアの継続
- privacy、security、保存期間、削除
- 課金、返金、解約、法務表示
- Production統制、監視、安全縮退、費用上限
- 外部検証の完了証拠
- 運用訓練と7日不在耐性
- AI権限境界
- 未解決P0 / P1がないこと

非免除条件のいずれかに影響する未解決P2は、修正と再レビューが完了するまで受容できない。チェック項目を「少人数βだから」「運用者が受容したから」という理由で免除しない。

### Public Releaseの非免除条件

Public Release / General Availability開始時は、適用されるSection 14または15の全安全条件と判定手続きを非免除条件とする。Section 15の対象以外で、有料β実績がないことを理由にSection 14を任意の非該当扱いにしてはならない。

適用する判定の非免除安全条件に影響する未解決P0 / P1 / P2、または重大なsecurity / privacy incidentがある状態では一般公開しない。

### 延期可能な項目

有料β後へ延期できるのは、次のような本書のチェック項目外の拡張だけとする。

- 招待管理画面の自動化
- 自動更新サブスクリプション
- 永続家庭マスタ
- 高度なanalytics dashboard
- 自動返金・自動解約
- 複数料金プラン
- App Store / Google Play

延期項目は開始前に列挙し、責任者、期限、利用者影響、代替手順を記録する。結果を見た後に基準を緩和しない。

## 1. 商品価値

- [ ] 家庭内で5回連続、重大な誤購入がない。
- [ ] 買い忘れがない、または導入前より明確に減っている。
- [ ] 買い物中の確認連絡が原則1回以下である。
- [ ] 依頼者の入力・管理時間がLINE等より大幅に増えていない。
- [ ] アプリ効果と、買い手が店舗・商品へ慣れた効果を区別して記録している。
- [ ] 写真、途中更新、条件表示が必要だった具体的場面を説明できる。
- [ ] 卒業による離脱と、不満・複雑さによる離脱を区別できる。

## 2. 無料コア

- [ ] 固定依頼は補助機能やAIサービスが停止しても作成・閲覧できる。
- [ ] 商品名、数量、条件、売場順をURL共有できる。
- [ ] 購入進捗は購入者端末で継続できる。
- [ ] 写真取得失敗でテキスト依頼を失わない。
- [ ] v5取得失敗時に最後の正常snapshotを表示できる。
- [ ] 手書き解析障害が通常依頼へ波及しない。
- [ ] 家庭マスタを書き出し・復旧できる。
- [ ] サービス終了時にも、サーバー依存を停止して無料コアを残せる。

## 3. ホスティングと環境

- [ ] 独自ドメインを使用する。
- [ ] 有料機能をGitHub Pagesで提供しない。
- [ ] Cloudflare Pages等の商用利用可能なホストへ移行している。
- [ ] 旧ドメインの家庭マスタを新ドメインへ移行できる。
- [ ] stagingとProductionを分離している。
- [ ] mainへのmergeだけではProductionへ反映されない。
- [ ] Productionは人間が承認し、人間が自分で実行する。
- [ ] stagingで確認したcommit SHAまたは成果物とProductionを対応付けられる。
- [ ] 最後の正常版へ戻す手順がある。
- [ ] migrationと通常リリースを分離している。

## 4. 外部検証の完了証拠

初期の有料β判定では、結果を見る前に次の基準を固定する。

### Phase 1: 外部課題インタビュー

- [ ] 条件に合う外部参加者5人以上へ、過去の具体的な買い物依頼について聞いている。
- [ ] 5人中3人以上で、確認連絡、誤購入、買い忘れ、依頼断念、写真送付等の中心課題が再現している。
- [ ] 仮定上の利用意思ではなく、過去行動と現在の代替手段を記録している。
- [ ] 対象者条件、質問項目、完了基準を募集前に記録している。

### Phase 2: 有償モニターによるClosed Alpha

- [ ] 原則3世帯を対象とし、各世帯で実際の買い物を3回行う計画を開始前に固定している。
- [ ] 3世帯中2世帯以上が予定回数を完了している。
- [ ] 完了世帯で、確認連絡または誤購入・買い忘れが導入前より改善している。
- [ ] 依頼者の作業時間が導入前より増えていない。
- [ ] 報酬がなくても継続利用したい世帯が1世帯以上存在する。
- [ ] 技術的失敗、friction、低頻度、no-value、graduatedを区別している。
- [ ] 基準未達時に、有料βへ進まず停止・再設計する判断を記録している。

人数、回数、閾値を変更する場合は、参加者募集前に理由と代替証拠を記録する。結果を確認した後の遡及的な緩和は禁止する。

## 5. 外部クローズドαの安全性

- [ ] 開発者用manual validationと外部参加者用alpha accessを分離している。
- [ ] 1世帯ごとに別の招待トークンを発行する。
- [ ] 招待に期限、feature scope、失効状態がある。
- [ ] 通常URLでは実験機能を公開しない。
- [ ] 参加者向けの試験説明、保存期間、注意事項がある。
- [ ] 同意後にだけ実験機能を有効化する。
- [ ] 参加を中止できる。
- [ ] 問い合わせ先がある。
- [ ] α終了後に招待を失効し、保存データの扱いを説明できる。

## 6. データとプライバシー

- [ ] 収集するデータと収集しないデータを一覧化している。
- [ ] 写真、依頼、capability tokenをログへ出さない。
- [ ] AIへ写真、商品名、条件本文、自由記述、完全な共有URL、token、Secret、cookie、authorization header、個人情報、支払い識別子、生support本文、request / response body、providerの生error、private Issue / PR / Runbook / repository検索結果を渡さない。
- [ ] AIはprivate operational repositoryを閲覧、検索、fetch、取得しない。AIへ渡す運用情報は、[`AI_AGENT_POLICY.md`の「AI-safe export」](AI_AGENT_POLICY.md#ai-safe-export)をcanonical definitionとして、version管理されたallowlist schema、決定論的producer、型・値範囲・未知field拒否・全禁止field不存在を確認する決定論的validator、validator成功後だけの送信、queue / artifactへの同一条件をすべて満たす。人間の目視、匿名化、仮名化、hash化、実名除去だけを安全条件にしない。
- [ ] 実験サマリーは商品内容を含まず、件数・エラー等に限定する。
- [ ] 参加者情報と公開リポジトリを分離する。
- [ ] データ削除依頼の受付と人間による実行手順がある。
- [ ] 写真と更新可能依頼の保存期間を利用者へ表示する。
- [ ] 解約、期限切れ、サービス終了後のデータ扱いを説明できる。
- [ ] プライバシーポリシーを公開している。

## 7. セキュリティ

- [ ] Git履歴全体をSecret scanしている。
- [ ] GitHub Secret Scanning / Push Protectionを確認している。
- [ ] CodeQLまたは同等のcode scanningが有効である。
- [ ] `SECURITY.md`がある。
- [ ] WorkerのOriginとTurnstile検証を維持している。
- [ ] Turnstileだけに依存せずRate Limitingを実装している。
- [ ] request size、商品数、写真枚数、更新回数、AI解析回数にサーバー側上限がある。
- [ ] security headerを設定している。
- [ ] capability URL漏えい時の説明と失効方法がある。
- [ ] Secret変更とローテーションは人間だけが行う。

## 8. 監視と安全縮退

- [ ] synthetic health checkが個人情報を送らずに動作する。
- [ ] エラーコードはallowlist化され、利用者本文を含まない。
- [ ] 写真、v5、手書き解析を個別に停止できる。
- [ ] 新規作成を止めても、既存の最後の正常データを表示できる。
- [ ] 利用量・費用にアプリ側のハード上限がある。
- [ ] Freeまたは予算上限到達時の挙動をテストしている。
- [ ] kill switchの操作対象と順序が文書化されている。
- [ ] 停止中の利用者向け表示がある。

## 9. AI支援運用

- [ ] CodexへProduction権限を与えていない。
- [ ] Codex実装・レビューセッションは専用branch、test、Draft PR、レビュー、修正、rollback案までに制限され、自分が作成、変更、または必須レビューしたPRをmergeしない。
- [ ] GitHub接続済み操作役AIによるmergeは、権限を持つ人間のexact repository / PR / base / headに対する明示承認と`AI_MERGE_APPROVAL.md`の全条件へ拘束される。
- [ ] 無承認merge、auto-merge、merge queue、branch protection・required checks・review gateの迂回を禁止している。
- [ ] 操作役AIはmerge直前にbase、head、Draft、mergeable、必須CI、独立レビュー、findingを再取得し、`expected_head_sha`等でhead移動を拒否する。
- [ ] 承認後にbase、head、差分、CI、レビュー結果が変われば承認と必要なレビューを失効させ、完全な再確認と再承認を要求する。
- [ ] AIはProduction反映、Production workflow、外部設定変更、顧客送信、返金、解約、利用者data操作を実行しない。
- [ ] AI-safe障害サマリーのschemaとexport手順があり、前節のcanonical AI-safe export条件を緩和しない。
- [ ] CI失敗から再現テスト、修正Draft PRまでの標準手順がある。
- [ ] Medium / High risk変更に別コンテキストレビューがある。
- [ ] base / head SHA変更時にレビューを無効化する。
- [ ] focused testとfull CIが成功している。
- [ ] mergeとProduction反映を別に承認し、mergeは人間または全条件を満たす別の操作役AI、Production反映は人間だけが実行する。
- [ ] AIサービスが停止した場合の手動縮退手順がある。
- [ ] AI利用費は当面ChatGPT Plusの範囲である。

## 10. 一人運用

- [ ] 通常時の日次手動確認が不要である。
- [ ] 週次作業が原則30〜60分以内である。
- [ ] 問い合わせはメールまたはフォームで、即時回答を約束しない。
- [ ] サポート時間を計測している。
- [ ] 依存更新を週次等へまとめられる。
- [ ] Production deployを必要時だけ人間が実施する。
- [ ] 緊急停止手順が1ページで実行できる。
- [ ] 運用者が対応できない場合の回復コードと連絡方法がある。
- [ ] 運用者が7日不在でも無料コアが継続する。
- [ ] 7日不在時に費用が暴走しない。
- [ ] 7日不在時に補助機能が危険な状態で動作し続けない。

## 11. 課金と顧客対応

有料βでは最初に一つの商品、一つの価格だけを扱う。

- [ ] 外部αとは別の利用者が実際に支払う申込をしている。
- [ ] 決済情報をアプリで保存しない。
- [ ] 価格、提供期間、提供内容を明示する。
- [ ] 返金、キャンセル、利用期限の方針がある。
- [ ] 特定商取引法上の表示を用意する。
- [ ] 利用規約を用意する。
- [ ] 問い合わせ記録を公開Issueへ置かない。
- [ ] AIが返金、解約、顧客送信を実行しない。
- [ ] 永続家庭マスタや自動更新サブスクリプションを同時導入しない。

## 12. 運用訓練

有料β開始前に、次の演習を実施し、開始時刻、検知、縮退、復旧、人間作業時間を記録する。

- [ ] 写真API障害
- [ ] v5取得障害
- [ ] 手書きAI障害
- [ ] 大量アクセス
- [ ] 利用量・費用急増
- [ ] 重大な依存脆弱性
- [ ] 誤ったProductionリリース
- [ ] capability URL漏えい
- [ ] AI利用不能
- [ ] 運用者7日不在

## 13. 有料β開始判定

有料βを開始できるのは、以下をすべて満たす場合だけとする。

1. Sections 1〜12の全チェック項目を完了している。Section 14は有料β開始判定の対象外である。
2. Phase 1とPhase 2の事前固定した基準を満たし、証拠を記録している。
3. 未解決P0 / P1がない。
4. Sections 1〜12の非免除条件に影響する未解決P2がない。影響しないP2だけ、根拠、責任者、期限を記録したうえで人間が受容できる。
5. 有料βの商品と価格に、Closed Alphaとは別の利用者から実際の申込がある。
6. 人間がexact PR/headのmergeを明示承認し、自分または全条件を満たす操作役AIによるmergeを統制できる。Production変更、緊急停止、返金、顧客連絡は人間が実行できる。
7. 延期項目を開始前に固定し、利用者影響と代替手順を記録している。

「機能が完成した」「テストが多い」「AIが修正できる」「少人数だから」だけでは開始条件を満たさない。

## 14. Public Release / General Availability判定

Section 14は有料β開始判定の対象外であり、Paid Beta開始後の実績を用いて独立に判定する。Paid Betaの開始または成功だけでは一般公開を承認しない。有料・補助機能を通常の公開導線へ出す前に、次をすべて満たす。ただし、Section 15の狭い対象に当てはまる無料の商品写真だけは、Section 15で判定する。

- [ ] Paid Betaを事前に定めた期間運用している。
- [ ] Paid Betaの対象世帯数、利用回数、継続率、終了理由を記録している。
- [ ] 未解決P0 / P1 / P2と重大なsecurity / privacy incidentがない。
- [ ] 変動原価とサポート時間が、一般公開後も個人で維持可能である。
- [ ] 7日不在訓練とProduction rollback訓練を再確認している。
- [ ] 一般公開後の価格、規約、privacy、返金、終了方針を公開している。
- [ ] 一般公開向けのRate Limit、費用上限、停止手順を検証している。
- [ ] 一般公開後もStable Free Coreを独立して維持できる。

Public Releaseは、Section 14の全項目と、別に定める判定記録を人間が確認し、人間が公開操作を実行した場合だけ開始する。

具体的な期間、世帯数、継続率、原価上限、サポート時間上限はPaid Beta開始前に別の判断記録で固定し、結果確認後に緩和しない。

## 15. 無料の商品写真だけの初回公開判定

2026-10-24のユーザーによる明示的な見直し依頼に基づく。Section 14の事業実績を後から達成済みにする変更ではない。
対象は、料金・課金・AI解析を伴わず、写真なしの固定依頼へ戻せる、1商品1枚/1依頼最大3枚/14日保持/v4参照の既存商品写真だけ。
v5、手書き、他のサーバー機能、有料化、保存範囲の拡張にはこの判定を流用しない。

無料写真の初回公開に、有料βの販売実績、世帯数、継続率、課金/返金実績、7日間の運用演習を前提とはしない。
代わりに次の安全条件と、非機密の判定記録を必要とする。

- [ ] exact base/headの必須CIと独立read-only Codexレビューが完了し、安全条件に影響する未解決P0/P1/P2がない。
- [ ] 本番から分離した実Cloudflare環境で写真の添付→共有→取得→表示が成功し、review対象codeとの対応が取れる。
- [ ] 写真0枚v3/1〜3枚v4、4枚拒否、Origin/Turnstile/action/hostname、MIME/容量/不正JPEG、冪等再送、timeout/取得失敗時の縮退、14日削除、既存URL/購入/進捗の回帰を自動/runtime/browserで確認している。
- [ ] 少なくとも1種類の実スマホで共有・表示・拡大・購入とLINE経由を確認する。他の端末、撮影/HEIC、別端末等の未確認範囲を明記し、未検証を成功・全端末対応と表示しない。
- [ ] 画像の圧縮/向き/EXIF除去と、写真・Secret・token・完全共有URL・利用者本文をログ/AIへ出さない境界を確認する。初回アップロードから14日の閲覧期限と削除予定、障害/無料枠による削除遅延、URL転送、バックアップ等を利用者説明と照合する。削除失敗後の再予約と復旧後の削除を検証し、全storage write拒否で再予約も失敗する場合の人間復旧手順を用意する。この回復証拠は公開前条件とし、無条件の14日物理削除を保証しない。
- [ ] Turnstileだけに任せず、サーバーで枚数・画像/MIME・容量・保持期間を強制する。無料枠の強制上限と障害時の縮退を確認し、独立Rate Limitの有無・限界を判定記録に残す。
- [ ] 無料plan・自動課金されない構成を人間が確認する。アカウント共用枠の残量、停止閾値、確認担当を記録する。有料plan/新サービスへの変更はこの判定の承認対象に含めない。
- [ ] 写真flagの停止・復旧と設定不足時の閉鎖を検証し、Worker/Pagesの操作順を1ページで実行できる。写真停止中も固定依頼・購入・家庭マスター復旧を維持する。
- [ ] 既存DO class/binding/SQLiteとlifecycleを照合し、既存namespace・migration・保存データを破壊せずにreview済みcodeを配置できる。配置commitとWorker version/Pages artifactを対応付ける。
- [ ] 人間が未確認範囲・残余risk・適用する無料公開条件を確認し、mergeとProductionを別に判断する。AIの自己merge禁止、ready化・Production・Secrets・法的公開の人間実行、private ops/データ境界は維持する。

独立Rate Limitがない初回の小規模公開では、上記のサーバー制限、Freeの強制上限、停止・縮退の証拠を必須とする。
これは世界全体の厳密な受付上限でも、濫用やquota枯渇を防ぐ保証でもない。共用枠の枯渇で写真や他の補助機能が停止するriskを明示し、
運用者・次回確認日・停止閾値を公開前の記録へ固定する。閾値超過、異常な利用増、監視できない場合は新規写真受付を停止し、
独立Rate Limit等を追加・検証するまで拡大しない。既存データの削除や有料upgradeで対処しない。

実端末の追加確認と7日不在演習は、今回の初回公開では延期理由・担当・次回確認日を明記できる。
privacy/security/14日削除、費用の強制上限、無料コア独立性、実staging、CI/独立レビュー、停止・復旧を延期できるという意味ではない。
判定の具体例と人間の最終操作は[無料写真の公開票](../PRODUCT_PHOTO_FREE_RELEASE.md)を参照する。
