# プロダクト検証戦略

Status: approved direction.

## 中心仮説

普段買い物を担当しない家族が、家庭固有の選び方を受け取り、確認連絡と買い間違いを減らし、一人で買い物を完了できる。

機能追加数ではなく、不確実性が減ったことを前進として扱う。

各Phaseの対象人数、実利用回数、成功基準は募集開始前に固定する。結果を見た後に基準を緩和しない。

## 現在の制約と検証境界

- 同一ブラウザ・同一端末などで複数のタブから同じローカル状態を更新した場合、last-writer-wins相当の競合が起こり得る。複数利用者間のトランザクション整合性は保証しない。
- WebKit系ブラウザ、BFCache / page restore、clipboard、OSネイティブ共有 / Web Shareの挙動は、自動testだけで実機上のすべての動作を保証しない。必要に応じて手動・端末検証の対象とする。

## Phase 0: 家庭内実験

対象は開発者本人と同居家族。実際の日常買い物で、迷い、確認連絡、誤購入、買い忘れ、依頼者側の準備時間を記録する。

家庭内で必要な改善は `personal-experiment` として試してよい。ただし、家庭内で役立っただけでは一般機能へ昇格させない。

完了基準:

- 5回連続で重大な誤購入がない。
- 買い忘れがない、または明確に減少する。
- 確認連絡が原則1回以下になる。
- 依頼者の準備時間が従来手段より大幅に増えない。
- アプリ効果と、経験や店舗への慣れを区別して説明できる。
- 写真、途中更新、条件表示が必要だった具体的場面を記録している。

Phase 0の完了は、外部課題の再現性または課金性を証明しない。

## Phase 1: 外部課題インタビュー

知人である必要はない。条件に合う外部参加者から、過去の具体的な買い物依頼、確認連絡、誤購入、買い忘れ、写真送付、依頼を諦めた経験を聞く。

「このアプリがあれば使うか」という仮定質問を主要証拠にしない。

初期計画:

- 対象者5人以上
- 買い物担当が同居者間で偏っていること
- 過去の具体的な行動と現在の代替手段を確認すること

完了基準:

- 5人中3人以上で、確認連絡、誤購入、買い忘れ、依頼断念、写真送付等の中心課題が再現する。
- 問題の発生頻度、現在の対処、依頼者側と買い手側の負担を記録している。
- 想定した対象者と実際の対象者が一致しているか評価している。
- 中心課題が再現しない場合、Phase 2へ進まず対象者または価値仮説を再設計する。

人数または閾値を変更する場合は、募集前に理由と代替証拠を記録する。

## Phase 2: 有償モニターによるClosed Alpha

原則1世帯ずつ開始し、合計3世帯を初期基準とする。開発者が参加者へ謝礼を支払う。

必要条件:

- 世帯ごとの期限付き招待
- 参加説明と同意
- 各世帯で実際の買い物を3回行う計画
- 終了後に招待を失効する
- 固定依頼、写真、途中更新を必要に応じて試す
- 開始前に導入前の確認連絡、誤購入、買い忘れ、依頼作成時間を記録する

完了基準:

- 3世帯中2世帯以上が予定した3回を完了する。
- 完了世帯で、確認連絡または誤購入・買い忘れが導入前より改善する。
- 依頼者の作業時間が導入前より増えない。
- 報酬がなくても継続して使いたい世帯が1世帯以上存在する。
- 技術的失敗、friction、low-frequency、no-value、graduatedを区別できる。
- 基準未達時に、有料βへ進まず停止・再設計する判断を記録する。

有償モニターの好意的評価を、課金性の証拠にしない。

人数、買い物回数、閾値を変更する場合は、参加者募集前に理由と代替証拠を記録する。結果確認後の遡及的な緩和は禁止する。

## Phase 3: 有料β

Closed Alphaとは別の利用者を募集し、利用者が料金を支払う。Phase 1とPhase 2の完了基準、および `docs/operations/PAID_BETA_READINESS.md` の非免除条件を満たすまで開始しない。

最初は一つの商品、一つの価格、一回払いとする。永続家庭マスタ、自動更新サブスクリプション、複雑な料金表を同時導入しない。

Paid Beta開始前に固定する項目:

- 対象世帯数
- 提供期間
- 最低利用回数
- 継続率または完了率
- 重大事故の許容数
- 変動原価上限
- 1世帯当たりサポート時間上限
- 停止・返金条件

評価基準:

- 実際の支払いが発生する。
- 事前に定めた割合の世帯が複数回利用する。
- 依頼者と買い手の双方で効果が確認できる。
- 他家庭への紹介が実際に発生する、または明確な紹介意思と対象が確認できる。
- サポート時間と変動原価を個人で維持できる。
- privacy、security、課金、Productionに関する未解決P0 / P1がない。

基準未達の場合、機能追加を自動的な解決策とせず、対象者、価値、導入負担、価格、提供方法のどこが原因かを再評価する。

## Phase 4: Public Release / General Availability

Paid Betaの成功だけで、有料機能または補助機能を通常の公開導線へ出さない。Stable Free Coreの継続と、有料・補助機能の一般公開を別の判断として扱う。

Public Release開始前に、次を事前固定して満たす。

- Paid Betaの最低運用期間
- 対象世帯数、実利用回数、継続率
- 重大security / privacy incidentがないこと
- 変動原価とサポート時間の上限
- 7日不在訓練とProduction rollback訓練の完了
- 一般公開後の価格、規約、privacy、返金、終了方針
- 一般公開向けRate Limit、費用上限、kill switch
- Stable Free Coreを独立して維持できること

結果確認後に一般公開基準を緩和しない。基準を満たさない場合はPaid Betaを継続、縮小、停止する。

## Phase 5: 継続保管・同期の判断

次の証拠が出た場合だけ永続家庭マスタを検討する。

- 有料βまたはPublic Release利用者から具体的な同期・保管要求がある。
- ローカル書き出しでは不十分な理由がある。
- 複数世帯が年額等を実際に事前購入する。
- バックアップ、削除、解約、アカウント回復を個人で運用できる。

要望や仮定回答だけで実装しない。

## 最小指標

買い物単位で次を記録する。

- 参加者コード
- app versionまたはcommit SHA
- 商品件数
- 写真使用件数
- 途中更新回数
- 確認連絡回数
- 買い忘れ件数
- 誤購入件数
- 依頼作成時間
- 買い物完了時間
- 次回も利用したか
- 終了理由

商品名、条件本文、写真、共有URL、capability tokenは収集しない。

実験記録をAIへ渡す場合も、private ops repositoryを直接読ませない。AI入力は[`AI_AGENT_POLICY.md`の「AI-safe export」](../operations/AI_AGENT_POLICY.md#ai-safe-export)をcanonical definitionとして、version管理されたallowlist schemaに従う決定論的producerが生成し、型・値範囲・未知field拒否・全禁止field不存在を決定論的validatorが確認した、validator成功後のpayloadだけに限定する。queue / artifactにも同じ条件を適用し、人間の目視、匿名化、仮名化、hash化、実名除去だけではAI-safeとみなさない。

## 効果の分解

成功時は、次を区別する。

- アプリの写真や条件が助けた。
- 前回の経験を覚えていた。
- 店舗に慣れた。
- 依頼者の説明が改善した。
- 代替判断を習得した。

「買えた」という結果だけで有料機能を決めない。

## 離脱の分類

- `graduated`: 習得し、詳細支援が不要になった。
- `free-core`: 無料の件数・条件・並べ替えだけを継続する。
- `friction`: 入力や操作が面倒でやめた。
- `low-frequency`: 利用場面が少なかった。
- `no-value`: 効果がなかった。
- `technical-failure`: 不具合や互換性で使えなかった。
- `privacy-concern`: データや写真への懸念でやめた。

卒業と失敗を同じ離脱として扱わない。

## 機能ライフサイクル

- `personal-experiment`: 家庭内だけで試す。
- `product-candidate`: 他家庭にも再現する可能性がある。
- `alpha-approved`: 外部α向けの安全、説明、計測条件を満たす。
- `paid-beta-approved`: Phase 1、Phase 2、有料β非免除条件を満たす。
- `public-stable`: Public Release基準を満たし、一般規模で維持可能である。
- `retired`: 利用価値、保守性、安全性の理由で停止する。

家庭内で便利だった、支払いが一件あった、運用者が責任を受け入れた、という理由だけで昇格させない。

## 新規Issueに記録する項目

- 発生した具体的な失敗
- 発生回数
- 困った利用者
- 現在の代替手段
- 最小の解決方法
- 家庭内専用か一般候補か
- 無料、期間課金、継続課金の候補
- サーバー原価
- サポート負荷
- 成功指標
- 廃止条件

## 撤退・転換条件

次の場合、B2C有料サービス化を停止または再検討する。

- Phase 1で中心課題が外部参加者に再現しない。
- 無料でも2回目に使われない。
- Closed Alphaの完了基準を満たさない。
- マスタ作成が従来手段より明らかに面倒である。
- 依頼者側の作業時間が増える。
- 写真や更新があっても確認回数が減らない。
- 価格提示後に申込がない。
- サポートしないと利用が成立しない。
- 家庭ごとの要求が大きく異なり、共通商品に収束しない。
- Public Releaseに必要な原価・運用基準を満たさない。

この場合も家庭用Stable Free Coreは維持する。
